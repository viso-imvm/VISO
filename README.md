
The system consists of two modules:
- **Planner**: generates optimized multi-query execution plans.
- **Executor**: executes the generated plans on update streams.



## Prerequisites

### Planner
- CMake 
- C++17 
- Boost 

### Executor
- Java 11 
- Flink 1.13
- Scala 2.12
- Maven >= 3.8.4





## Quick Start

### 1. Build the Planner

```bash
cd planner
mkdir build 
cd build
cmake .. 
make 
```

This produces the executable `MQO_CROWN` in `planner/build/`:




### 2. Run the Planner



**Custom input file:**
```bash
./build/MQO_CROWN --input <input_file> --output-dir <output_dir>/
```

**Planner input file format.** The input file is a plain-text, whitespace-delimited file describing one or more free-connex queries.

```
<query_num>

<rel_num>
<rel_copy_id>  <label_id>  <attr_num>  <attr_id_1> <attr_id_2> ... <attr_id_{attr_num}>
<rel_copy_id>  <label_id>  <attr_num>  <attr_id_1> ... 
...
<output_attr_num>  <out_attr_id_1> <out_attr_id_2> ...

(repeat the rel block + output block for each query)
```

Field semantics:
- `query_num`: total number of queries in this file.
- `rel_num`: number of relation copies in the current query.
- `label_id`: identifies the relation *type* (i.e., which physical table). Multiple relation copies may share the same `label_id`; the planner may share plan nodes between them.
- `attr_num`: number of attributes in this relation.
- `attr_id_1 ... attr_id_N`: globally unique integer IDs for this relation's attribute columns. Two relations that share an `attr_id` express a **natural join** on that attribute.
- `output_attr_num`: number of projected output attributes for this query.
- `out_attr_id_1 ...`: the attribute IDs to include in the query's output (must be a subset of the union of all `attr_id`s in the query).

Example (2 queries, each a path join over relations with label 0):
```
2

3
1  0  2  1 2
2  0  2  2 3
3  0  2  3 4
4  1 2 3 4

3
5  0  2  5 6
6  0  2  6 7
7  0  2  7 8
4  5 6 7 8
```

Output files are written to the `output/` directory (or the specified `--output-dir`):
- `multi_query_plan.json` — multi-query (MQO) plan
- `query_schema_*.txt` — executor output schema

after generation, we should run planner/remove_empty_related_qs.py to delete redundant parts in the plan.

### 3. Build the Executor

```bash
cd executor
mvn clean package -DskipTests=true
```

This produces `executor/target/CROWN-1.0-SNAPSHOT.jar`.

### 4. Run the Executor

```bash
java -cp executor/target/CROWN-1.0-SNAPSHOT.jar GenericJob \
  --path <data_directory> \
  --graph <input_file> \
  --planFile <plan.json> \
  --schemaFile <schema.txt> \
  [--dataFormat <snb|job>] \
  [--deltaEnumEnable] \
  [--fullEnumEnable] \
  [--outputFile <output.txt>] 
```

**Arguments:**
| Argument | Description | Default |
|---|---|---|
| `--path` | Base directory of the input data file | (required) |
| `--graph` | Name of the input data file | (required) |
| `--planFile` | Path to the JSON query plan | (required) |
| `--schemaFile` | Path to the executor schema file | (required) |
| `--dataFormat` | Input format: `snb` or `job` | `snb` |
| `--deltaEnumEnable` | Enable delta enumeration | `false` |
| `--fullEnumEnable` | Enable full enumeration | `false` |
| `--outputFile` | Path for output tuples | `out.txt` |

**About the `schemaFile`.** The schema file has two parts concatenated in one text file: an **input schema** (top) and an **output schema** (bottom).

- The **output schema** is automatically produced by the planner (written to `query_schema_*.txt` next to the plan JSON). It tells the executor which attributes each query should output.
- The **input schema** is **not** generated by the planner — it depends on how the raw data file is laid out, so it has to be written by hand (or by a small data-specific script). It tells the executor, for each relation in the plan, which raw columns to read.

To build the final `schemaFile`, write the input-schema lines first, then append the planner-generated output-schema content.

**Input schema format** — one line per non-`generalized` relation in the plan:

```
<eventTag>,<relationName>,<keyIndex>,<colIdx1>,<colIdx2>,...
```

- `eventTag`: a tag on each input row that selects the rows belonging to this relation. For SNB this is one of `PE` (person), `ME` (message), `KN` (knows), `TA` (tag), `MT` (message_tag). For JOB this is the base table name (e.g. `title`, `cast_info`, `movie_info_idx`).
- `relationName`: the relation name as it appears in the plan JSON (e.g. `person1`, `knows2`, `title1`).
- `keyIndex`: the index of the primary-key column in the raw row.
- `colIdx1,colIdx2,...`: the indices of the raw-data columns that should be loaded into this relation's tuple. The order here defines attribute index 0, 1, 2, … which is exactly what the output schema then references.

**Output schema format** (planner-generated, kept as-is):

```
<numQueries>
<queryId_0>
<relationName>.<placeId>,<attrIdx>
<relationName>.<placeId>,<attrIdx>
...
<queryId_1>
<relationName>.<placeId>,<attrIdx>
...
```

Each `<relationName>.<placeId>,<attrIdx>` line refers to the `attrIdx`-th column of `relationName` as defined by that relation's input-schema line above.

**Example schema file** (`schema_files/snb_mqo.txt`, abbreviated):

```
KN,knows1,1,1,2          # input schema: KN events feed knows1, key=col1, load cols 1,2
PE,person1,1,1,2,3       # PE events feed person1, key=col1, load cols 1,2,3
ME,message1,1,1,8
...
4                        # output schema starts: 4 queries
0                        # query 0
person1.0,1              # query 0 outputs person1's attribute 1
person1.0,2
message1.0,0
1                        # query 1
...
```

**Example:**
```bash
java -cp target/CROWN-1.0-SNAPSHOT.jar GenericJob \
  --path ~/data \
  --graph ldbc.csv \
  --planFile query_plans/snb_mqo.json \
  --schemaFile schema_files/snb_mqo.txt \
  --deltaEnumEnable \
  --outputFile snb_out.txt
```



### Input Data Format

**SNB format** (pipe-separated):
```
+|R|f1|f2|...|fn    # insertion (R = relation name, e.g. TA, ME, ...)
-|R|f1|f2|...|fn    # deletion
```

**JOB format** (comma-separated):
```
1 R f1,f2,...,fn       # insertion
0 R f1,f2,...,fn       # deletion
```
